# JT-22 (follow-up to JT-07: confirmation layout): JT's work log

### 2026-10-28 — JT-22: Space and surface confirmations tied to a workout layout
- **Done:** Fixed the issue Yadan found in her review of PR #47: a space confirmation recorded for one workout layout
  (e.g. the running lane) turned a later plan's space check with another layout (e.g. stationary) into `pass`.
  `src/server/lifecycle/confirmations.ts` now works out a plan's layout (`planLayout`), records the current plan's
  layout on a new confirmation (`confirmationLayout`; null if the confirmation is for another park or time), and
  only matches `space_surface.*` checks with the same layout. `service.ts` passes the plan's layout at every place
  confirmations are applied (generate, recheck, apply option, add confirmation), using the snapshot's templates.
  Tests for both directions, unknown layouts, and carry-forward with the same layout.
- **Decisions:** D-JT22-1 in `docs/decisions/JT-22.md`.
- **Interfaces others depend on:** additive contract change: `OrganizerConfirmation.layout` (optional, nullable;
  set by the harness, not by the API request). API request shapes are unchanged.
- **Unfinished / next:** JT-09: move confirmations into the snapshot as `organizer_confirmation` evidence so the
  workout rules decide (one way to confirm), and drop the lifecycle matching.
- **Gotchas:** a confirmation for a park or time other than the current plan's (e.g. answering an alternative's
  organizer task before applying it) has no known layout, so it does not carry to that option once applied; the
  organizer confirms again on the new version. Safe, but one extra step until the task names its layout.
- **Requests:** Yadan: for JT-09, the organizer task and confirm request will need to say which layout they ask about.
