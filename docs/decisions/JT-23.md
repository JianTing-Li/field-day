# JT-23 decisions (follow-up to JT-17: fixes from the first real eval run)

### D-JT23-1 — Passing checks decide readiness, not the agent's status
- **Date / owner:** 2026-10-28 · JT
- **PRD section:** §3 "The harness owns all state"; §3a check_plan; §3b Planning Agent
- **Decision:** A new version whose plan passes every check is `ready_for_approval`, whatever status the agent
  returned. Before this, an agent's `needs_verification` kept an all-pass plan from approval. The agent's
  concerns and organizer tasks stay on the version, so the organizer still sees them before approving.
  Unknown or failed critical checks still never give `ready_for_approval`; there the agent's
  `no_feasible_option` is kept. The eval runner grades Planning alone and the 4-agent workflow with the same
  `deriveStatus`, so the evals match what the app does.
- **Why:** in the first real run (Haiku), Planning returned `needs_verification` on Case 1 and Case 4 although
  all 10 checks passed. Its blocking concerns were demo-wide limitations that are already labeled everywhere:
  the workout template is pending instructor review, the park record is a fixture placeholder, and the heat/AQI
  policy is unreviewed. None of them can be resolved for a single event, so they would block plans that pass every check. A real
  gap the agent notices belongs in check_plan as a check, not in free-text status.
- **Value:** `deriveStatus(plan, checks, agentStatus)`: all-pass checks → `ready_for_approval`
- **Status:** in use

### D-JT23-2 — Output limit per model request
- **Date / owner:** 2026-10-28 · JT
- **PRD section:** §3 "Execution budgets"
- **Decision:** The agent runner asks for at most 16,384 output tokens per model request (was 4,096). In the
  first real run, Logistics and Reviewer answers on conflict cases were cut off at 4,096 and rejected as
  `invalid_output`. The per-run budget (60,000 output tokens, D-004) still caps the total.
- **Value:** `DEFAULT_MAX_TOKENS = 16_384`
- **Status:** in use
