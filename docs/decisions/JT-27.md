# JT-27 decisions (repair old demo events, 2026-11-02)

### D-JT27-1 — The current code replaces demo events seeded by old code
- **Date / owner:** 2026-11-02 · JT (decided with the human)
- **Problem:** after "Reset database" on 2026-11-02 (emptied at 16:27:55 UTC), the three demo events were written
  again at 16:28:37 UTC by code from before JT-24: "(Case N fixture)" names, July dates and July weather (93°F).
  The live domain runs current code, so the writer was another copy of the app sharing `DATABASE_URL` (Vercel
  previews need a Vercel sign-in; nothing on JT's Mac ran then). The current code only seeded missing events, and
  Neon kept the first snapshot saved under an ID, so the old July snapshot stuck too.
- **Decision:**
  - A demo event whose name is still its scenario's fixture name (`isLegacySeed` in the lifecycle service) is
    replaced in place by a fresh seed: plain name, upcoming date, fall weather, Case 1 locked in. The check runs at
    seeding, and again when the event list or that event is read, so a running server repairs old seeds written
    after it started.
  - The Neon store overwrites a snapshot saved under an existing ID (`ON CONFLICT … DO UPDATE`), as the memory store
    already did. Live snapshot IDs are hashes of their evidence, so only demo snapshots (fixed IDs) can change.
- **The writer:** Vercel's request logs show `GET /api/events` at 11:28:36 ET (16:28:36 UTC) on
  `field-lm8evbbzo-calm-forge.vercel.app`, the Oct 29 preview of commit 616d3f6 ("JT-24: work log, decisions, README
  and TASKS", branch `fix/jt-24-audit-fixes`), from a Mac browser, with Neon queries. Previews share the live
  `DATABASE_URL`. Scope `DATABASE_URL` to Production in Vercel so previews and old deployments can't write to it.
- **Status:** in use
