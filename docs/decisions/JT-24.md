# JT-24 decisions (fixes from the whole-app audit, 2026-10-29)

### D-JT24-1 — Only space, surface and permit can be confirmed
- **Date / owner:** 2026-10-29 · JT
- **PRD section:** §4 "Organizer confirmation resolves only the stated check; it does not fabricate provider
  evidence"; §3 "Missing or failed API data… critical gaps block finalization"
- **Decision:** An organizer confirmation can only resolve `space_surface.space`, `space_surface.surface` and
  `permissions.permit_review` (`CONFIRMABLE_CHECK_IDS` in `src/contracts/checks.ts`). The API rejects any other
  check with 400, `applyConfirmations` ignores stored confirmations for other checks, and the UI only offers
  Confirm for those three, taken from the harness's own unknown checks instead of agent-written to-dos.
- **Why:** the audit locked in a production event dated Dec 15, which had no weather or air-quality data, by
  "confirming" heat, AQI and freshness with one sentence each. The UI offered the same through an agent to-do
  ("yes it's confirmed" on a heat check).
- **Value:** `CONFIRMABLE_CHECK_IDS = [space, surface, permit]`
- **Status:** in use

### D-JT24-2 — Demo labeling in every data mode
- **Date / owner:** 2026-10-29 · JT (decided with the human)
- **PRD section:** §3 "Validation Policies" (unreviewed values "cannot support real-world finalization");
  MVP scope (unreviewed workout content is excluded)
- **Decision:** Lock-in stays available, so the demo keeps its happy path. But the "Demo" banner shows in live
  mode too (unreviewed limits and workouts), and a locked-in record gets `demo_only: true` while it rests on the
  unreviewed demo policy, a template pending instructor review, or fixture data. The page then says "Saved as your
  final plan in this demo… don't run a real event on it."
- **Rejected:** blocking lock-in until review (kills the demo); switching production back to fixtures (the
  recorded data only covers Oct 27–28).
- **Status:** in use

### D-JT24-3 — The harness computes every version's checks; agents don't write them
- **Date / owner:** 2026-10-29 · JT
- **PRD section:** §3 "The harness owns all state"; §3a check_plan
- **Decision:** `generateDraft`, `applyOption` and non-material brief edits compute `check_plan` themselves (with
  confirmations applied) instead of storing the checks an agent returned. The specialists and the Reviewer leave
  each option's `checks` out of their answer (`src/server/agents/model-output.ts`); parsing fills a pending
  placeholder that the enforce step replaces, as it already did. The Reviewer uses the supplied combination checks
  instead of calling `check_plan` again, and ranks at most 3 options.
- **Why:** stub fixtures' option checks left out the surface check, so a plan showed "Overall: Pass", was approved,
  and then failed the save gate with no way to confirm the surface. On production a conflict review took 90–104 s
  and about 200k tokens, and once was cut off at the output limit, mostly writing checks that were thrown away.
- **Status:** in use

### D-JT24-4 — Generate runs the whole workflow
- **Date / owner:** 2026-10-29 · JT
- **PRD section:** §3 "Workflow at a glance"; "When the harness or the organizer finds a conflict"
- **Decision:** Generate calls `runWorkflow` (Planning, the conflict check, then the specialists and Reviewer when a
  critical check fails) instead of Planning alone, so a conflict arrives with its alternatives. Seeding the demo
  events always uses the stub agents, so a page view never spends model credits and the demo is the same every time.
- **Why:** the app never ran the automatic path; only the evals did, so the eval numbers described a workflow users
  didn't get.
- **Status:** in use

### D-JT24-5 — Editing only the name, notes or priorities keeps the plan
- **Date / owner:** 2026-10-29 · JT
- **PRD section:** §2 "Reopen the event; edits create a new draft version… Material changes invalidate approval"
- **Decision:** An edit that changes only the title, the instructor's free-text notes or the priorities creates a
  new version that keeps the plan, its checks (recomputed) and the confirmations; approval has to be given again
  because the version changed. Any other edit is material: no plan, confirmations cleared, and the page drafts a
  new plan straight away.
- **Status:** in use

### D-JT24-6 — Safety limits can only be stricter, in the form too
- **Date / owner:** 2026-10-29 · JT
- **Decision:** The form refuses a max temperature above 90°F or an AQI above 100 (or below 0). The rules already
  ignored looser values (`effectiveLimit`), so an organizer who typed 100°F believed a limit that never applied.
- **Status:** in use

### D-JT24-7 — Session length and type come from the workouts
- **Date / owner:** 2026-10-29 · JT (decided with the human)
- **PRD section:** MVP scope (2–3 instructor-reviewed templates; unreviewed exercise content excluded)
- **Decision:** Length is chosen from the lengths the workouts can run (30, 35, 45 minutes today: each template's
  duration and its permitted adaptations), and the workout picker moves up as "Type of session". When the event's
  name asks for an activity FieldDay has no workout for (yoga, pilates, dance…), the form says so and lists what it
  will plan instead, and the Planning prompt treats the title as a name, not an activity request. No new
  activities until an instructor reviews them.
- **Why:** every template is 45 minutes and adaptations only shorten it, so a 90-minute event always ended in "No
  workable option", with advice to change the date or parks. "Sunrise yoga" also made the agent refuse every
  template.
- **Status:** in use

### D-JT24-8 — Events beyond the forecast range
- **Date / owner:** 2026-10-29 · JT (decided with the human)
- **Decision:** Allowed. The plan is drafted and the next step says it's too early for a forecast and when to check
  again, instead of a list of coverage errors. Past dates are rejected by the API as well as the form (a saved past
  date on an older event can stay while other fields are edited).
- **Status:** in use

### D-JT24-9 — Keep the 10 curated parks
- **Date / owner:** 2026-10-29 · JT (decided with the human)
- **PRD section:** MVP scope ("A curated set of 3–5 park candidates")
- **Decision:** Keep the 10 parks in `content/parks.json` (settles D-020). No park search, zip-code lookup or

- **Status:** superseded by D-JT24-13 (2026-10-30)

### D-JT24-10 — Input limits and rate limits
- **Date / owner:** 2026-10-29 · JT
- **Decision:** Request bodies over 32 KB are refused. Briefs: name ≤ 120 characters, length ≤ 240 minutes,
  group ≤ 500, lists ≤ 20 items of ≤ 200 characters, notes and statements ≤ 500 characters, change reports ≤ 1,000.
  Agent routes check the body before taking an agent run, so a malformed request never uses up quota. Creating
  events has its own limit in every mode: 20 per visitor per hour, 300 a day.
- **Why:** the audit used up the agent quota locally with 18 junk requests and stored a 200,000-character title.
- **Value:** `MAX_BODY_BYTES = 32_000`, `INPUT_LIMITS`, `EVENT_CREATION_LIMITS`
- **Status:** in use

### D-JT24-11 — Rain check (a PRD change)
- **Date / owner:** 2026-10-30 · JT (decided with the human; Yadan to agree)
- **PRD section:** §3 "Validation Policies" lists heat and air quality only. This adds a row.
- **Decision:** A new critical check `weather.rain` fails when the NWS hourly chance of precipitation is over
  40% for any hour of the event, is unknown when an hour has no forecast, and, like heat, can't be fixed by a gentler
  workout. The value is an unreviewed demo policy (`POLICY_CONFIG.rain`). The 12 scenario fixtures predate the
  rule, so the fixture registry adds a 10% rain forecast for every recorded temperature hour; no case's expected
  outcome changes, and the tool tests keep using the raw case files.
- **Why:** rain is the most common reason an outdoor class is moved, and the app fetched the rain chance but never
  checked it: a 90% storm forecast passed.
- **Contract:** adds `weather.rain` to `CheckId` and `rain` to `PolicyArea`. Several tables are keyed by every
  check ID, so under CLAUDE.md this counts as a breaking contract change; it's in this PR at the human's request
  and is called out for Yadan's approval.
- **PRD updated 2026-10-30:** the Validation Policies table has a Rain row under Heat: "Reviewed chance-of-rain
  threshold, source field (NWS hourly probability of precipitation), and applicability to the full event interval."
- **Status:** in use

### D-JT24-12 — "Something changed?" reports change the checks
- **Date / owner:** 2026-10-29 · JT
- **PRD section:** §2 workflow ("Request a recheck or report a change"); §4 "Organizer confirmation resolves only
  the stated check"
- **Decision:** "Something changed?" sits on the event page whenever there is a plan, locked in or not. A report
  can name one check: space or ground at this park, rain or the start time at this time
  (`REPORTABLE_CHECK_IDS`). That check then fails there (`applyReports`) in every later check, the gate included,
  until a newer confirmation for the same check and park supersedes it. A report always adds a new version, so a
  locked-in plan stays saved, and the review runs on that version. The review's options are re-checked with
  reports and confirmations before they're shown, since the agents' check_plan tool sees only the evidence
  snapshot. Equipment and group-size changes edit the brief and draft again. "Something else" is context for the
  agents only.
- **Status:** in use

### D-JT24-13 — 29 curated parks with a search picker (a PRD change)
- **Date / owner:** 2026-10-30 · JT (decided with the human; Yadan to agree)
- **PRD section:** MVP scope ("A curated set of 3–5 park candidates"); Excluded ("Broad venue discovery")
- **Decision:** The curated list grows to 29 parks from NYC Open Data's Parks Properties (every borough), each with a
  coordinate checked to fall inside the park's boundary. The brief form picks parks with a search box, borough
  chips, and "Near me" or a zip code that sorts the list by distance. One event considers at most 5 parks
  (`MAX_PARKS`, `INPUT_LIMITS.parks_per_event`). Distances come from stored coordinates and a bundled table of NYC zip
  centres (`nyc-zip-centroids.json`, from MODZCTA); nothing is looked up online, and the browser's location never
  leaves the page.
- **Why:** 10 parks didn't cover most of the city, and a checkbox wall doesn't scale past that. Each park in an event
  adds forecasts and options for the agents to weigh, so the cap keeps runs inside their budget.
- **PRD updated 2026-10-30:** MVP scope reads "A curated, searchable list of NYC parks (29 today), of which one event
  considers up to 5"; the exclusion now says broad venue discovery means finding parks beyond the curated list, and
  that sorting the list by distance is in scope; `get_park_candidates` reads "the event's curated candidates (up to 5)".
- **Status:** in use

### D-JT24-14 — Demo events have plain names and upcoming dates
- **Date / owner:** 2026-10-30 · JT
- **Decision:** The three seeded events are named like real events ("Morning bodyweight class", "Run club
  intervals", "Early bodyweight class") instead of "(Case N fixture)", and are dated 2, 3 and 4 days after the day
  they're seeded when their recorded date has passed. The scenario's evidence and the stub agents' recorded answers
  move by the same number of days (`shiftDate`), so each event tells the same story as its eval case. The eval cases
  themselves keep their recorded dates.
- **Why:** a demo whose events are dated in the past or labeled as test fixtures reads as broken.
- **Known gap (resolved by D-JT24-16):** Cases 2 and 3 are July heat scenarios (93°F, 92°F); moved to November they
  were implausible.
- **Status:** in use

### D-JT24-15 — Beginner outdoor yoga, pending instructor review
- **Date / owner:** 2026-10-30 · JT (decided with the human; Yadan agreed to changes in his files)
- **PRD section:** MVP scope (instructor-reviewed templates); Excluded (unreviewed exercise content as approved)

  activities until an instructor reviews them" for this one activity, at the human's request.
- **Status:** in use

### D-JT24-16 — The demo events show fall weather: rain instead of a heat wave
- **Date / owner:** 2026-10-30 · JT (decided with the human)
- **Decision:** The seeded demo events' recorded weather is shown as late fall weather (`inFallWeather` in
  `src/server/lifecycle/snapshots.ts`). Hours over 70°F lose 30°F, and every hour that was over 90°F gets an 80%
  chance of rain. The same hours fail, on rain instead of heat: "Run club intervals" fails at 10 a.m. and the
  suggested fix is 8 a.m.; "Early bodyweight class" passes on its first forecast and the refreshed one turns rainy.
  The 12 eval cases keep their recorded July weather, so no eval result changes.
- **Why:** with D-JT24-14's upcoming dates, the demo showed 92°F in November.
- **Status:** in use
