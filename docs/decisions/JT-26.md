# JT-26 decisions (forecast-pending lock-in, 2026-11-02)

### D-JT26-1 — Lock in when only an unpublished forecast is missing
- **Date / owner:** 2026-11-02 · JT (decided with the human; PRD updated the same day)
- **PRD section:** §3 tool contracts ("Unknown critical checks block finalization"), check_plan, final save gate
  ("No critical check is failed or unknown"); each now names this exception.
- **Problem:** AirNow's current web service publishes air quality for today only (checked live on 2026-11-02:
  `/aq/forecast/current/` returns the Nov 2 forecast, even with a later `date`; the dated services return HTTP 410).
  With "unknown blocks lock-in", nobody could lock in an event before its day.
- **Decision:** A plan is lock-ready (`lockReady` in `src/server/lifecycle/transitions.ts`) when every critical check
  passes, or nothing fails and every open critical check is a forecast that can't exist yet
  (`isForecastPending` in `src/contracts/checks.ts`): air quality for any later day, weather (heat, rain) beyond
  `WEATHER_FORECAST_DAYS` (6). The freshness check only counts alongside one of those. The status is
  ready_for_approval, the gate passes `current_evidence` and `hard_constraints` with "Forecast not out yet, to check
  closer to the day: …", and the finalized record lists `pending_checks`. The badge reads "Finalized, forecast
  pending"; the event page says when each forecast comes out and offers "Check the forecast" once it's due.
- **Still blocked:** any failed check; a stale or missing forecast that should exist (weather within 6 days, or the
  event day itself); anything an organizer must confirm.
- **Rejected:** background reminders or notifications (the PRD excludes background monitoring and messaging); the
  reminder is on the event page when the organizer opens it.
- **Supersedes:** the "Rejected" note in D-JT25-2.
- **Status:** in use

### D-JT26-2 — A passing recheck keeps a locked-in plan locked in
- **Date / owner:** 2026-11-02 · JT
- **Decision:** "Check the forecast" on a locked-in event refreshes the evidence. New evidence adds a recheck version
  as before; if that version is lock-ready, it is approved and locked in again through the same gate
  (`lockIn` in the lifecycle service), since the organizer already approved this exact plan and only the forecast
  changed. If the new forecast fails, the plan stays unlocked and the page shows what to fix.
- **Status:** in use

### D-JT26-3 — Evals judge forecast-pending as of the day the evidence was gathered
- **Date / owner:** 2026-11-02 · JT
- **Decision:** `harnessStatus` in `evals/runner.ts` passes the snapshot's `created_at` date as "today", so results
  never depend on the clock. Case 10 (outside forecast coverage, gathered 2026-10-28) now expects ready for approval
  ("draft"), overall unknown, finalize allowed and no gate failures; Planning still reports needs_verification.
  This is the one expected outcome changed after its first run, because the PRD rule it tests changed.
- **Status:** in use
